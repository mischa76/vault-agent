# WP23 — Incremental vault extension, Phase 1 (brownfield mode)

Status: Proposed · Size: L · Depends on: — (independent of WP22) ·
Source: `incremental-extension-charter.md` (Accepted; §5 decisions 2026-07-29)

Binding charter decisions: **Q1 extension run** (the modeler emits only the delta,
existing constructs are immutable context) · **Q2 grandfathering** (existing names and
bindings survive a hub going multi-source) · **Q3 flagged migration** (attribute growth
on an existing satellite is never silent) · **Q4 delta-ADR** with an "Extends" section ·
**Q5 one review queue**, new kind. Phase 2 (LLM entity resolution) is a later spike —
in Phase 1 the human answers the "is this the existing hub?" question via the existing
ratification surface; Phase 1 must be honest where it cannot know.

## 1. Scope

One new mode: `vault-agent run <doc> --existing <dir|file> [...]` extends a previously
generated vault. Greenfield behaviour stays byte-identical without the flag (the
ADR-0004 inertness pattern; the guard test is written FIRST). Foreign-vault
introspection (models not generated by vault-agent) is Phase 3 — out of scope.

## 2. Target design [ENFORCE]

### 2.1 The logical model becomes a first-class output (round-trip source)

`cli.write_outputs` additionally writes `metadata/dv_model.yml` =
`state.dv_model.model_dump()` — the LOGICAL model (descriptions, requirement_ids,
driving keys, sat_type, sources, source_table, …), which `automatedv.yml` (rendered
macro metadata) cannot losslessly yield. This refines the charter's §3.1
("automatedv.yml round-trip"): the rendered metadata stays what it is; the round-trip
source is the logical dump. Deterministic, sorted keys; counts gains `"model": 1`.

New loader `src/vault_agent/existing_model.py: load_existing_model(path) -> DVModel` —
accepts an output directory (reads `metadata/dv_model.yml`) or a bare YAML file; house
loader style (attributable ValueError naming file + problem); absent/empty → `None`.
A directory WITHOUT `dv_model.yml` (pre-WP23 output) is an attributable error telling
the user to regenerate once with the current version — never guessed from automatedv.yml.

### 2.2 State + CLI

`state.existing_model: DVModel | None = None` (checkpointer-safe — the serde allow-list
picks DVModel up already). CLI `--existing/-e` on `run` (resume needs nothing: persisted
in the checkpoint). The orchestrator's `ExecutionPlan` gains `extending: bool` and the
run summary prints `mode: extension (N existing construct(s))` / `greenfield`.

### 2.3 Extension-run modeling (charter Q1)

`dv2_modeler._build_system_prompt` gains an extension section when `existing_model` is
set: a compact inventory of existing constructs (hub name + BK + sources; link name +
grain + roles + driving key; sat name + parent + type) marked IMMUTABLE, plus
instructions: map new requirements onto existing concepts where they match; emit ONLY
(a) new hubs/links/satellites and (b) an existing hub re-stated BY NAME carrying ONLY
additional `sources` entries (the S1 "new feed" case). New steering rules go through the
WP16 registry (origin: this spec; the prompt fixture is updated deliberately, WP20
precedent). Attributes that belong to an existing satellite's concern go into a NEW
satellite on the same parent (charter Q3) — steered, and gated below.

### 2.4 Deterministic merge

New module `src/vault_agent/agents/model_merger.py: merge_models(existing, delta,
state) -> DVModel` (deterministic, keyless):

- New constructs (names not in existing) append, in delta order after existing order.
- A delta hub matching an existing hub by name is an EXTENSION: only `sources` entries
  not already present are applied (dedup per E_HUB_DUP_FEED semantics); ANY other
  difference (BK, source_entity) is ignored for the merge and flagged
  (`FlagKind.EXTENSION_CONFLICT`, error) — the gates fail the run.
- A delta link/satellite matching an existing name is flagged EXTENSION_CONFLICT
  (error): links and satellites are never extended in place, only added.
- The merge NEVER mutates `existing_model` (it stays the comparison baseline).

The merged model is what code generation, validation, mapping, and the ADR see.

### 2.5 Additive gates (charter §3.3, over (existing, merged))

Validator gains, active only when `state.existing_model` is set:

- `E_EXISTING_REMOVED` — an existing construct is absent from the merged model.
- `E_EXISTING_BK_CHANGED` — an existing hub's business_key/source_entity changed
  (normalised comparison).
- `E_EXISTING_GRAIN_CHANGED` — an existing link's participation multiset (hub, role) or
  driving key changed.
- `E_EXISTING_SAT_RESHAPED` — an existing satellite's parent/type/cdk/source_table
  changed or its attribute set changed IN ANY WAY (growth included — charter Q3: never
  silent; shrink and growth are both migrations).
- `W_EXISTING_EXTENDED` — advisory inventory, one per legitimate extension (a hub that
  gained feeds; each net-new construct attached to an existing parent), construct as
  the issue's construct. This is the review queue's extension category (charter Q5 —
  validation warnings already flow into the queue; no new ReviewKind needed).

These are invariants over the merge output — unreachable violations today, insurance
against merger bugs and any future re-model mode.

### 2.6 Grandfathering in generation (charter Q2)

When an EXISTING single-source hub becomes multi-source through the extension:

- The ORIGINAL feed keeps the legacy staging model name (`stg_<base>`, no source
  suffix); only NEW feeds get `stg_<base>_<source>` (WP10 naming). Derivation is
  deterministic from `existing_model` (a feed's presence there = legacy naming) — no new
  state field.
- Existing satellites keep their names and their binding to the legacy staging model —
  they are NOT split per source. Only NEW satellites on that hub follow WP10
  sat-per-source naming against the new feeds.
- The hub's `source_model` list = [legacy staging, new per-source stagings]; its SQL
  legitimately changes — the diff (§2.7) names it.
- Greenfield multi-source (hub born with `sources` in one run) keeps symmetric WP10
  naming — grandfathering applies only to constructs present in `existing_model`.
  Guard: the WP10 tests and the mapping/bank demos stay byte-identical.

### 2.7 Diff artifact + report

New deterministic renderer (presentation-only): `extension-diff.md` written by
`write_outputs` when extending — three sections: unchanged (count + collapsed list),
extended (per construct: what was added — feeds, new children; which FILES changed
content for a pre-existing construct, computed by comparing rendered artifacts against a
regeneration of `existing_model` alone), new (full list with parents). The HTML report
gains an "Extension" section rendering the same data (report.py conventions: escape
everything, no new script). The run summary prints the three counts.

### 2.8 Delta-ADR (charter Q4)

`adr_author`, when extending: the ADR documents ONLY the delta (new/extended constructs
with requirement traces) plus an "Extends" section — source of `--existing` (path as
given), its construct counts, and a pointer to the diff artifact. Unchanged constructs
are not re-listed. Still ADR-0001-per-output, deterministic.

### 2.9 Pipeline placement

The merge runs inside the modeler node after `_validate_model` (the modeler owns
`dv_model`; graph.py stays orchestration-only). Contracts/mapping operate on the merged
model as today — the mapper's concept list naturally includes existing constructs'
concepts only where sources are declared; Phase 1 does not change mapper behaviour.

## 3. Tests (all keyless; the LLM stays injectable)

1. **Inertness FIRST:** no `--existing` → every artifact byte-identical (extend the
   staging-regression pattern; run before any other change lands).
2. Round-trip: bank demo model → `dv_model.yml` → `load_existing_model` →
   `merge_models(existing, empty delta)` → regenerate → byte-identical project.
3. Merger: new constructs append; hub feed extension dedups; BK/grain/sat conflicts →
   EXTENSION_CONFLICT flags; existing model never mutated.
4. Gates: each `E_EXISTING_*` triggered by a hand-built violating merged model;
   `W_EXISTING_EXTENDED` inventory matches a mixed S1+S2 extension.
5. Grandfathering: existing hub + new feed → legacy staging name kept, existing sat
   unsplit and bound unchanged, new sat per new source; greenfield WP10 naming
   byte-identical (existing WP10 tests untouched).
6. Diff artifact: pinned fixture for a mixed extension; file-change attribution names
   exactly the hub SQL (not the untouched sats).
7. Delta-ADR: extends-section content pinned; unchanged constructs absent.
8. CLI: `--existing` with dir/file/missing/pre-WP23 dir (attributable error);
   summary line; counts gain `model` + diff artifact.

## 4. Acceptance criteria

1. Greenfield byte-identity (test #1) and WP10/demo guardrails pass untouched.
2. `bank_extension` eval case added (charter §6): existing bank vault + CRM schema +
   extension requirements; golden = merged model; scorers: existing-construct
   preservation 1.0 (deterministic), extension construct F1 via the existing scorers.
3. Postgres hardness (maintainer, live): extension output builds green ON TOP of the
   previously built bank vault — `dbt build` WITHOUT full-refresh on pre-existing
   tables; pre-existing row history intact; the new link/sat populated. Recorded in
   CLAUDE.md before the WP is called done.
4. Standard DoD.

## 5. Out of scope

Phase 2 (LLM entity resolution, same-as candidates — spike per charter), Phase 3
(foreign-vault introspection), destructive migrations (detected + flagged only),
mapper changes, UI beyond the report section.
