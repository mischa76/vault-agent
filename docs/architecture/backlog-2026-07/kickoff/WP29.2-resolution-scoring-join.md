WP29.1 made `brownfield_resolution` **runnable**. It is not yet **scoreable**: the first live
probe (1 repeat, ~$0.60, `docs/log.md` 2026-08-01, the correction entry) came back
`GATE UNSATISFIABLE`. The mechanism looks good — the resolver answered **all seven traps
correctly, including trap 5** — and no scorer can see it. This WP closes that, and only that.

**Two of the four items are DECISIONS, and one of them is not yours to make alone.** Read §1 and
§3 before writing code; if the human has not answered §3, build everything else and stop there
rather than changing the measure on your own authority.

## 1. The join — DECIDE, then implement

The resolver speaks before anything binds a business concept to a physical table. Its key is
`business_entity::column` (`partner::partn_nr`); the golden is `(source_table, source_key)`
(`vic_partner`, `partn_nr`). Measured in the live probe: **the column half matched 7/7, the
table half 0/7.**

| route | mechanism | the cost, stated honestly |
|---|---|---|
| **A** column only | match on the normalised key column | `crm_guid` and `partn_nr` each appear **twice** in the probe's proposals (the xref table is answered too), so it mis-attributes precisely where the case is hardest |
| **B** via the mapper | resolver's column → `state.mappings.proposals[].entity` → physical table → golden | uses the pipeline's OWN binding (`{"column": "kontakt_id", "entity": "vic_kontakt", "category": "exact_name", "confidence": 0.99}`) rather than inventing one. But it couples the resolution score to mapper quality, and WP25 routes a failing model past the mapper — so the join is absent exactly when the run went badly |
| **C** golden-side anchor | the golden declares the identifying column and the loader asserts it is unique within the case | keeps the scorer pure; changes the MEASURE, so it needs its reasoning written down first |

No route is pre-selected. Whichever is taken, **write the reasoning down before the code** and
say what would falsify it. B is the most principled and the most coupled; A is the one that
looks obvious and fails in the two places that matter.

## 2. `resolution_accuracy` must tell a miss from an answer

Today an unmatched golden entry reads as `unresolved` — and trap 5 *expects* `unresolved`, so
the probe scored 1/7 having measured nothing. A miss must be a miss, whatever route §1 takes.
Pin it with a test that fails if a not-found entry ever scores as correct.

## 3. Does the golden cover `crm_xref_partner`? — the HUMAN decides

The probe answered `migration_assignment::crm_guid -> hub_customer`. Writing CRM GUIDs into the
customer hub is the dangerous direction, and the xref has no golden entry, so WP29.1's
out-of-universe rule lets it pass unexamined. Two defensible readings:

- the xref row *is* a customer, so the merge is right and the golden is merely silent; or
- the CRM GUID is a foreign key space — which trap 4 already says for `crm_kunde` — so this is
  a false merge the golden fails to catch.

The golden was written **before the mechanism existed**, and that is what makes it worth
something. Extending it after seeing an answer is exactly the move `.claude/rules/eval.md`
warns about ("do not weaken a gate because a run came out badly" — and its mirror, do not
strengthen one to catch a specific answer). **Do not decide this in code.** Put the question to
the human with both readings; if unanswered, leave the golden untouched and record that the
xref is unmeasured.

## 4. The blinded probe has no case

§4 acceptance #3 wants the blinded re-run showing accuracy falling while `false_merge_rate`
holds. No blinded variant exists — the spike blinded by removing column comments. Build
`brownfield_resolution_blind` (or a declared variant of the same case), and apply WP29.1's own
guard pattern to it: a test proving it differs from the clean case in **exactly** the column
comments and in nothing else. A blinded case that also changed a type or a table silently
measures something else.

## Verify

- `uv run pytest -q`, `uv run ruff check .`, bare `uv run mypy` — green, no API key set.
- Mutation-check the join: reverting it must fail the new tests **and nothing else**.

  traps are already on disk in `eval/results/brownfield_resolution/`. The instrument must score
  **7/7** on them before anyone pays for a fresh run. If it does not, the join is still wrong.
