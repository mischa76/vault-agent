## What to build (all keyless)

1. **Strip the trap annotations out of `source_schema.yml`** into a sibling file
   (`trap-annotations.md` or similar). They duplicate `golden_resolution.yml`'s own
   `rationale` fields, so nothing is lost. Measured already: the schema loader discards
   comments, so the pipeline never saw them and no past score is affected — **pin that** with
   a test asserting the cleaned file loads identically to the annotated one (same tables,
   columns, types, column comments).
2. **Re-author `requirements.md` blind** against the cleaned file, per WP30 §2.4a: the
   authoring agent receives ONLY the cleaned `source_schema.yml` — not the golden, not the
   existing vault, not the log. Keep the current draft beside it (e.g.
   `requirements.draft-2026-08-01.md`), unusable header intact — it is the record of why the
   re-authoring was needed. Records are append-only; do not delete it.
3. **Write `dataset.yml`** so `--dataset brownfield_resolution` starts: brownfield mode
   against `existing_vault.yml`, declared schema `source_schema.yml`, the new requirements.
   Verify the production loaders on the wired paths (`load_existing_model` →
   `hub_customer`/`hub_account`; schema → 8 tables) — both already verified loadable, so a
   failure here is your wiring, not the fixture.
4. **Fix the scorer matching** — the WP14 fix, applied to resolution. The pipeline emits
   `entity::field` concept keys; the golden carries `concept` labels plus `source_table` /
   `source_key`. Match on **`(source_table, source_key)`**, which `split_concept_key` gives
   you from the pipeline's key and the golden already carries. And fix the fail direction
   explicitly: today an unmatched proposal lands in `offenders`, so every correct merge would
   have scored as a false one. An unmatched proposal is **out of universe** (the WP14
   semantics), not a false merge. `false_merge_rate` stays a hard property over the matched
   universe; report the unmatched count in `details` the way `mapping_coverage` does.
5. **Dispatch the resolution scorers** in `_score_run` by the `golden_resolution.yml`
   convention — the counterpart of the `golden_mapping.yml` dispatch. A case that has the
   golden but produces no resolutions must score 0, loudly; a case without the golden skips
   the family, and (per the run.py:307 guard's spirit) a resolution case whose golden is
   missing must fail the run, not silently pass it.
6. **Tests for 4 and 5**: pipeline-shaped keys against the real golden — a correct merge
   scores 1.000, a wrong-target merge 0.000, an unmatched proposal is reported but does not
   score as false; dispatch fires on this dataset and stays inert on mapping-only cases.
