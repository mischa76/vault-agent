# Charter — incremental vault extension (brownfield mode)

Status: Accepted (§5 decisions taken 2026-07-29) · Type: track charter (Phase 1 =
speccable WP work, Phase 2 = timeboxed design spike, Phase 3 = deferred) ·
Decision maker: Mischa Eismann ·
Origin: discussion 2026-07-29; relates to ADR-0010 Option C

## 1. Why this track exists

vault-agent is a pure greenfield tool today: every run models into an empty target. But
non-destructive extensibility is *the* selling point of DV2.0 — the everyday enterprise
scenario is extending an EXISTING vault: a new source system feeding already-modelled
entities, or new entities (from a new or known source) attaching to existing hubs.
An agent that only does greenfield misses the case practitioners actually live in.

Second motivation, recorded so it is not rediscovered: incremental use is the
methodically correct answer to the scale axis. ADR-0010's Option C (domain partitioning)
and this track are the same feature seen from two sides — nobody models 300 tables in
one pass; they model domain by domain into a growing vault. A working brownfield mode
relieves the pressure on ever-larger single-shot modeling long before streaming's model
output limits become the binding constraint.

## 2. Scenarios in scope

- **S1 — new source, existing entity:** a second/third source system feeds an existing
  hub (e.g. a CRM joins the legacy system on `hub_customer`). Mostly WP10 machinery
  (`Hub.sources`, canonical key, sat-per-source) — what is missing is arriving there
  FROM an existing model instead of within one run.
- **S2 — new entities, existing vault:** new hubs/links/satellites (from a new or
  already-integrated source) attach to existing constructs — a new `hub_claim` linking
  to the existing `hub_policy`.
- **S3 — mixed:** a new source brings both (typical real project).

Out of scope for the whole track: destructive refactorings of an existing vault
(satellite re-splits, BK changes, hub merges/splits). Those are migrations, not
extensions — the agent may DETECT and flag that the requirements imply one, but never
performs it (ADR-0007 assist-boundary logic applied to structure).

## 3. Design cornerstones (positions to confirm, not yet decisions)

### 3.1 The existing model is an input, not a discovery

New optional input `--existing <output dir | automatedv.yml>` → typed
`state.existing_model: DVModel`. The cheapest reliable source is vault-agent's OWN
output: `metadata/automatedv.yml` already encodes every construct machine-readably, so
Phase 1 is a round-trip loader (`automatedv.yml → DVModel`) in the
`source_schema.load_source_schemas` style (attributable errors; empty/absent → inert).
The ADR-0004 pattern binds: with no `--existing`, every path stays byte-identical —
greenfield remains the default mode and the regression guard.

Foreign vaults (not generated by vault-agent) are Phase 3: reverse-engineering AutomateDV
projects / DDL is the same introspection work already deferred in the roadmap — this
charter does not move it forward, it only reserves its seat.

### 3.2 Regenerate, don't patch

The generator is deterministic, so the output strategy is: merge (existing + new) →
regenerate the FULL project → the diff IS the deliverable. Unchanged constructs render
byte-identically (the existing determinism guarantee does the heavy lifting), so
"regenerate everything" is data-safe: unchanged SQL means unchanged tables. No delta-file
machinery, no patching, the whole existing codegen stays untouched. The run report and a
new diff artifact (`extension-diff.md`) present: unchanged / extended / new constructs,
and — critically — any FILE-level change to a previously existing model.

### 3.3 Additive gates (deterministic, the product half)

DV2.0-additivity is checkable without an LLM. New validator gates over
(existing_model, merged_model), all `E_` unless noted:

- `E_EXISTING_REMOVED` — an existing construct is missing from the merged model.
- `E_EXISTING_BK_CHANGED` — an existing hub's business key (or source_entity) changed.
- `E_EXISTING_GRAIN_CHANGED` — an existing link's participations/roles changed.
- `E_EXISTING_SAT_RESHAPED` — an existing satellite's parent/type/cdk changed or its
  attribute set SHRANK (growth is a design question, see §5 Q3).
- `W_EXISTING_EXTENDED` — advisory inventory of every legitimate extension (new source
  feed on an existing hub, new sat on an existing parent), for the review queue.

The modeler is steered ("these constructs exist — reuse, never re-invent or rename"),
but the gates are the guarantee; steering-vs-backstop bookkeeping follows WP16
conventions (registry entries with origin = this charter).

### 3.4 File-level vs. vault-level additivity — the grandfathering question

Additive at vault semantics can be non-additive at file level: adding a second source to
a single-source hub changes the hub's `source_model` to a list, and WP10's naming would
split the existing `sat_x` into `sat_x_<source>` — a RENAME of a deployed dbt model, i.e.
destructive DDL on a table that has history. Position to confirm: **grandfathering** —
an existing satellite keeps its name/binding when its hub becomes multi-source; only NEW
per-source satellites get the WP10 suffix. The diff artifact must name every file whose
content changed for a pre-existing construct (the hub SQL legitimately changes), and the
E-gates must be defined on vault semantics, not file bytes. This is the trickiest design
decision of Phase 1 and needs Mischa's call (§5 Q2/Q3).

### 3.5 Entity resolution against the existing vault (the LLM half, Phase 2)

The genuinely new LLM task: is "Partner" from the new source the existing `hub_customer`
or a new hub? This is the WP9 mapping problem one level up — concept↔concept instead of
concept↔column — and the whole WP9 apparatus transfers: evidence trail, deterministic
confidence categories (exact-name > key-overlap > semantic), honest `unresolved`, HITL
ratification file, post-validation that never invents a construct. Same-as links (so far
explicitly deferred) become an expected OUTPUT here: two keys asserted-equivalent but
differing stay two hubs plus a flagged same-as candidate for human ratification — never
a silent merge. Mechanism choice (LLM-first vs. deterministic-first, calibration, the
golden-set traps) is spike territory; the mapping spike's protocol is the template.

## 4. Phasing

| Phase | Content | Type | Size (est.) |
|-------|---------|------|-------------|
| 1 | Round-trip loader, `--existing`, merged-model regeneration, additive gates, diff artifact, review-queue category, grandfathering decision | speccable WP after §5 decisions | M/L |
| 2 | Entity-resolution assist (concept↔existing-construct), same-as candidates, ratification | timeboxed spike → WP (spike-mapping-charter as template: golden set with traps — synonym hub, false-friend entity, legitimate new-hub-despite-similar-name; ≥5 repeats; honest-failure exit) | spike 2–3 agent-days, then M |
| 3 | Foreign-vault introspection (AutomateDV project / DDL reverse engineering) | deferred, own charter when pulled | L |

Phase 1 has no LLM risk (loader + gates + diff are deterministic; the modeler change is
one prompt section) and delivers standalone value: S1/S2 work today IF the human answers
the entity-resolution question themselves via the ratification file — Phase 2 only
automates the proposal.

## 5. Open design questions (decisions needed before the Phase-1 spec)

> **DECIDED 2026-07-29 (Mischa), all five per the recommended positions:** Q1 extension
> run · Q2 grandfathering (existing names preserved) · Q3 flagged migration (attribute
> growth on an existing satellite is never silent) · Q4 delta-ADR with an "Extends"
> reference · Q5 one review queue, new kind. The Phase-1 spec
> (`wp23-incremental-extension-spec.md`) binds these; the question texts below are kept
> for the reasoning record.

1. **Merge semantics of a re-run:** is `--existing` + requirements a pure EXTENSION run
   (modeler sees existing constructs as immutable context, models only the delta), or a
   re-model with protection (modeler re-emits everything, gates enforce additivity)?
   Position: extension run — cheaper, safer, and the re-model variant collides with the
   one-coherent-model output budget (ADR-0010) at exactly the wrong time.
2. **Grandfathering (§3.4):** confirm existing-name preservation when a hub goes
   multi-source; define which file-content changes to pre-existing constructs are
   acceptable (hub source list, staging derived columns) and how the diff presents them.
3. **Satellite attribute growth:** is adding attributes to an EXISTING satellite an
   extension (file change, hashdiff change → full-refresh semantics on that sat!) or a
   flagged migration? Position: flagged migration — a hashdiff change is not additive at
   the data level; new attributes belong in a new satellite unless a human decides
   otherwise. This is exactly the kind of DV2.0-practice question the methodology docs
   should answer with a citation, not a preference.
4. **Where the merged model's ADR lands:** the extension run's ADR-0001 documents the
   delta with references to the existing model's provenance — format to define.
5. **Checkpoint/HITL surface:** does the extension diff join the existing review queue
   (one more category) or warrant its own sign-off artifact? Position: same queue, new
   kind — one checkpoint, not two.

## 6. Measurement (how we know it works)

- **Determinism guard:** greenfield runs byte-identical without `--existing` (the
  ADR-0004-style inertness test, written FIRST).
- **Round-trip guard:** generate bank demo → load its automatedv.yml → regenerate →
  byte-identical project.
- **Extension case:** new golden eval case `bank_extension` — the existing bank vault +
  a CRM source schema + extension requirements; golden = expected merged model
  (hub_customer gains a source, one new hub + link + sats). Scorers: existing construct
  preservation (deterministic, must be 1.0), extension construct F1, and in Phase 2 the
  resolution accuracy/gap metrics per the mapping-spike pattern.
- **Postgres hardness (the house habit):** extension output builds green on the demo
  database ON TOP of the previously built vault — `dbt build` without full-refresh on
  pre-existing tables, proving data-level additivity, not just SQL-level.

## 7. Constraints

- Repo canon binds (CLAUDE.md): rules in `rules/`, typed flags, never silently guess,
  keyless testability for everything deterministic.
- Public-readiness: all case content anonymized (ATLAS convention).
- Greenfield behaviour stays byte-identical throughout — this track adds a mode, it must
  never tax the existing one.
- No UI work; the diff artifact is markdown + the existing HTML report section pattern.
