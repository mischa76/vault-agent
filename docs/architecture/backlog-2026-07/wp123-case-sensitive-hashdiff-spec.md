# WP123 — Case-sensitive hashdiffs: a satellite stores a change of case (C61, option b)

Status: **Approved and in progress** (2026-11-10, the owner chose option (b): vault-agent renders the hashdiff input
itself, keys stay case-insensitive) · Owner: Mischa Eismann · Author: Claude. Candidate C61.

## 1 What is wrong

C60 measured on a project generated by vault-agent: a source value changing from `gold` to `Gold` inserts nothing; the
satellite's newest value reads `gold` while the source holds `Gold`. AutomateDV 0.11.4 upper-cases every hash input
by default (`hash_content_casing: 'upper'`, `standard_column_wrapper.sql:8`) and offers one switch for hashkeys and
hashdiffs together (`hash.sql:25`, `null_expression.sql:13`). Data Vault wants keys case-insensitive and descriptive
attributes case-sensitive.

## 2 The rule

1. Every column a stage hashes **into a hashdiff** is first derived as the hex of its UTF-8 bytes, after AutomateDV's
   own standardisation minus the upper-casing: `<hex>(NULLIF(TRIM(CAST(<col> AS <text_type>)), ''))`, named
   `<COL>__CS`, and the hashdiff lists the derived names. AutomateDV then upper-cases a hex string — which carries no
   letter case of the value — and does the rest as before (column sort, `||`, `^^` for NULL, MD5). Measured on
   PostgreSQL 16.15 (2026-11-10): `gold` → `676f6c64`, `Gold` → `476f6c64`, ` gold ` = `gold`, `''` and NULL → NULL,
   `Zürich` → `5ac3bc72696368`.
2. `PlatformProfile.hex_text`: PostgreSQL `ENCODE(CONVERT_TO({}, 'UTF8'), 'hex')`, Databricks `HEX({})`;
   `<text_type>` is WP121's (`text`, `string`).
3. The column the expression reads: a column the stage already derives is read through its derivation (a WP121 cast,
   a WP82 alias's source column), a reserved column (WP79) through its quoted physical name — AutomateDV evaluates all
   derived columns in one select, so one derived column cannot read another.
4. **Hashkeys are untouched** — their input stays upper-cased, every hub and link key unchanged.

**Output-changing:** every hashdiff of every generated project changes. An existing vault's satellites receive one
row per key on the first load after the upgrade (the new hashdiff differs from the stored one), unless they are
rebuilt with `--full-refresh`. A minor release with a migration note.

## 3 Not done

Multi-active satellites hash the same way and are covered; effectivity satellites carry no hashdiff. C62 (effectivity
order) separate. Databricks is guarded by its spelling only, not built.

## 5 Measured (2026-11-10, keyless)

- **P1 ✔.** Five guards, four red at `c93c77f` (the key guard green before and after, as it should be); a sixth for
  the column gate, red at `e6edd31`.
- **P2 ✔, with one finding.** Suite with no key reachable 1719 passed / 5 skipped, ruff, bare mypy. The guards that
  changed, each deliberately and only in its hashdiff part: the two byte-identity baselines (`staging_ungrounded_
  baseline/` — `stg_account`, `stg_customer`; `greenfield_manifest.json` — those two and `automatedv.yml`; no
  raw-vault model changed), `test_multi_source_hub`, `test_staging_generator`, `test_target_platform` (the stages now
  differ across platforms in the hex lines only), `test_wp79_reserved_word_columns` (the hashdiff reads `GROUP__CS`,
  which reads `"group"`), four of `test_wp121_no_equality_types`. **Finding:** the validator's column gate
  `E_STAGE_COLUMN_NOT_IN_SOURCE` read every derived value as a source column name, so a generator expression failed
  it — WP121's `CAST(RESUME AS text)` already did (guard T6 red against the code before this WP: two errors on the
  `xml` relation), unnoticed because WP121 was measured on a regeneration without the validator. Fixed by a typed
  record: the stage metadata's `expression_reads` names the column each generator expression reads, and the gate
  judges that.
- **P3 ✔** C60's scenario: load D (`gold` → `Gold`) `INSERT 0 1`, contact 1's newest value `Gold`; A–C, E, F as before
  (`SELECT 2`, `INSERT 0 1`, `INSERT 0 0`, `INSERT 0 0`, `INSERT 0 1`).
- **P4 ✔** the twenty-fifth chain's fifth project: 75 stages differ (every stage with a hashdiff, nothing else), each
  of them equal to the pre-WP123 regeneration in the WP121 build, overlaid and built: **PASS=420 ERROR=1 SKIP=4**;
  `hub_business_entity` 20 779 rows as before; `sat_business_entity_person_name` 19 973 (19 972 + ghost),
  `sat_sales_order_details` 31 466 (31 465 + ghost).
- **P5 ✔** the bank demo: `build_vault_models.py` byte-identical, `dbt build --full-refresh` PASS=36.
- **Not measured:** Databricks (spelling guarded); an existing vault's first load after the upgrade (one new row per
  key per satellite is the expected cost — stated in the manual, not run).
