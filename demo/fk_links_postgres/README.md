# FK-derived links demo — translated and relationship-table links, built on local Postgres

This demo is the **runnable, keyless capture of WP36 and WP37**: links the pipeline derives from
a source's declared foreign keys — a surrogate→natural-key **translation** (ADR-0013,
[`wp36`](../../docs/architecture/backlog-2026-07/wp36-surrogate-key-translation-spec.md)) and a
**relationship-table link** with three participations, two of them translated
([`wp37`](../../docs/architecture/backlog-2026-07/wp37-relationship-table-links-spec.md)) —
generated by the real proposer, applier and code generator and built into a running Data Vault
on PostgreSQL. No API key.

> **Last verified:** 2026-09-13 on PostgreSQL 16 + AutomateDV 0.11.4 (dbt-core 1.9.10).
> `dbt build --full-refresh` green: `PASS=26 WARN=0 ERROR=0` (5 seeds, 8 views, 7 incremental
> models, 6 data tests). Every row of both links joins every hub it references (3 of 3 each);
> a second `dbt build` inserts 0 rows; an inserted `ProductVendor` row with an unknown
> `ProductID` fails the translation view's `not_null` and `relationships` tests (2 of 4 FAIL),
> which is the data-time gate ADR-0013 promised.
>
> **WP38 verified 2026-09-14** on the same stack: a subtype feed — `SalesPerson`, keyed on
> `Employee`'s surrogate, feeding `sat_sales_person_details` on `hub_employee` (keyed on
> `NationalIDNumber`). `PASS=35 WARN=0 ERROR=0`; both satellite rows join `hub_employee`; a second
> build green; an orphan `BusinessEntityID` fails both view tests (2 of 2).
>
> **The first build found two defects the keyless tests had not** (see [Findings](#findings)).

## What is fixed here, and what is computed

Fixed (hand-written, in `build_vault_models.py`): the prior vault (`hub_product` keyed on
`ProductNumber`, `hub_unit_measure`), the declared source tables with their foreign keys
(the AdventureWorks shape both WPs were measured on), and the delta the modeler would emit for
the increment (`hub_vendor` keyed on `AccountNumber`, `hub_shopping_cart_item`, one satellite).

Computed by the pipeline's own functions, in the pipeline's order — link proposer, checkpoint
(`--accept`), `apply_ratified_link_proposals`, `merge_models`, `CodeGeneratorAgent`,
`ValidatorAgent`, `rebind_staging`:

| Link | Shape | Staging |
|---|---|---|
| `link_shopping_cart_item_product` | WP36: `ShoppingCartItem.ProductID → Product.ProductID`, hub keyed on `ProductNumber` | `stg_shopping_cart_item_product` reads `..._via_product` (LEFT JOIN, projects `PRODUCTNUMBER`) |
| `link_product_vendor` | WP37: hub-less `ProductVendor` with keys to Product, UnitMeasure, Vendor; Vendor is this increment's table, so its participation is **pending** until `hub_vendor` exists | `stg_product_vendor` reads `..._via_product_and_vendor` (two LEFT JOINs, projects `PRODUCTNUMBER` and `ACCOUNTNUMBER`) |
| `sat_sales_person_details` | WP38: a satellite on `hub_employee` (NationalIDNumber) read from `SalesPerson`, whose key is `Employee`'s surrogate; the same-as is ratified and the join declared | `stg_sales_person_details` reads `..._via_employee` (LEFT JOIN, projects `NATIONALIDNUMBER`) |

Each translation view ships a `.yml` with `not_null` on the projected natural key and a
`relationships` test on the surrogate — the gates that make an unmatched surrogate fail
`dbt build` instead of hashing a NULL key.

## Runbook

Prerequisites as in [`demo/bank_postgres`](../bank_postgres/README.md): a local PostgreSQL with
the `vault` role/database, and `uv sync --extra demo` (dbt-core 1.9 + dbt-postgres).

```bash
cd demo/fk_links_postgres
uv run python build_vault_models.py      # regenerate models/ + scaffolding from the real generator
export DBT_PROFILES_DIR="$PWD"
uv run dbt deps                          # AutomateDV
uv run dbt build --full-refresh          # seed + run + test
```

The build writes into schema `fk_links_demo`. To see the translation at work:

```sql
set search_path = fk_links_demo;
select count(*), count(p.product_hk), count(v.vendor_hk), count(u.unitmeasure_hk)
from link_product_vendor l
left join hub_product p on p.product_hk = l.product_hk
left join hub_vendor v on v.vendor_hk = l.vendor_hk
left join hub_unit_measure u on u.unitmeasure_hk = l.unitmeasure_hk;   -- 3 | 3 | 3 | 3
```

## Findings

Recorded in `docs/log.md` (2026-09-13). The first `dbt build` of a translated link, ever:

1. **The generated `stg_*_via_*.yml` was not valid YAML.** `to: {{ ref('Vendor') }}` — Jinja
   braces unquoted in YAML are a flow mapping; dbt refused to parse the whole project. Every
   project with a translated link had been unbuildable since WP36 was built. dbt's form is
   `to: ref('Vendor')`.
2. **A link with two translated participations got one translation view.** The staging spec
   held a single translation slot; `ProductVendor`'s Vendor translation overwrote its Product
   translation, and the stage hashed `PRODUCTNUMBER` from a view that never projected it.

Both are pinned by `tests/test_translation_build_guard.py` (written failing first) and fixed
in `staging_generator.py`: a list of translations per stage, one LEFT JOIN each, one view
named `_via_<a>_and_<b>`.

**Observed, left alone:** the per-key proposals of a relationship table (`ProductVendor.ProductID`,
`.UnitMeasureCode`) are ratified by `--accept` and then flagged "not applied: no hub was
modelled for ProductVendor" — two advisory review items that say nothing the relationship link
does not already say. A reviewer sees them; nothing is wrong in the data.

The guard test `tests/test_demo_fk_links_postgres.py` keeps this capture from rotting.
